MCSU Console on AWS

Where the console runs, how a request reaches the database, how we deploy it, and the one decision left for go-live. Everything runs in AWS Singapore. Email and documents stay in our Microsoft 365, and the web address stays with our DNS provider.

How a request reaches the data

The browser first asks our DNS provider where the console lives, then connects straight to the load balancer over HTTPS. Each layer accepts traffic only from the layer in front of it, so the app server and database can't be reached from the internet.

Who is allowed to connect to what

Firewall rules (security groups) are chained. Nobody logs in to the server over SSH. Admin access goes through Systems Manager and is logged.

Web address and HTTPS production domain open · Q18

The domain stays with its current DNS provider. Per environment we add two records: one proves to AWS that we own the name (AWS then issues a free certificate that renews itself), and one points the name at the load balancer. Staging uses a domain we control now. Production uses the same method once its domain is chosen.

Deployment method: one-time setup

Done once for staging (roadmap milestone 1.1b), then repeated for production at go-live. All infrastructure is defined in Terraform, so both environments are built from the same files.

  1. Create the AWS account and team accessQNX AWS Org adminNew member account in the Organization; IAM Identity Center access for the team.
  2. Prepare Terraform stateDev leadAn encrypted, versioned S3 bucket that stores what Terraform has built.
  3. Build the infrastructureDev leadterraform apply: network, firewall rules, load balancer, EC2 server, RDS database, image registry, alarms, scheduled jobs, and the GitHub deploy role.
  4. Request the certificateTerraformAWS Certificate Manager issues a validation record for the subdomain.
  5. Add the validation recordWhoever manages DNSAdd the CNAME at the DNS provider (e.g. Hostinger hPanel → DNS). The certificate shows Issued within minutes to an hour.
  6. Turn on HTTPSDev leadRun terraform apply again: the load balancer's HTTPS listener uses the issued certificate, and HTTP redirects to HTTPS.
  7. Point the web address at the load balancerWhoever manages DNSCNAME staging-console → the load balancer's address (a Terraform output).
  8. Fill in secretsDev leadDatabase passwords, sign-in secret, Microsoft 365 app credentials and cron secret go into Parameter Store, never into files in the repo.
  9. Create the database usersDev leadOne user that can change the schema (used only for releases) and one read/write user for the app.
  10. First deployDev leadGitHub → Actions → Deploy → Run workflow. It creates the tables and the first Super Admin account.
  11. Smoke testTeamSign in, check the health page, install the phone app, send a test email.

Deployment method: every release

The same steps run for both environments. Staging updates automatically when a change is merged. Production updates only from a release tag, after a manual approval. It reuses the exact image that was tested on staging (no rebuild) and takes a database snapshot first.

What the deploy script does on the server

deploy.sh <version>
  1. load secrets from Parameter Store
  2. pull the new image from ECR
  3. run the migrate job (schema changes)
  4. start the new app
  5. wait for /api/ready (app + database)
     ✗ unhealthy → restart previous version

If something goes wrong

  • App broken after release: rolls back automatically. To pick a version yourself, re-run the Deploy workflow with an older version.
  • Data problem: restore the database to a point in time, check it, then point the app at it.
  • Server failure: AWS recovers the server automatically, and a new one can be rebuilt from the template in minutes.

Production go-live checklist

  • Production domain chosen and access to its DNS confirmed
  • Production account built (setup steps 1–9), certificate issued, console record live
  • App address settings point at the production URL
  • Restore-from-backup drill done once on the production database
  • Alarm emails confirmed, budget alert set
  • First release deployed with approval, smoke test passed
  • Staging users told that production is a separate address (sign in again, reinstall the phone app)

Keeping it running

Backups

  • Automatic daily RDS backups with point-in-time restore
  • Snapshot before every production release
  • Restore to a fresh database tested once a quarter

Monitoring

  • App logs in CloudWatch, errors in Sentry
  • Email alarms for site errors, unhealthy server, high CPU, low database storage, certificate not renewing
  • Hardware failure triggers automatic server recovery

Security & upkeep

  • Database private, encrypted, TLS required
  • No SSH, no stored AWS keys, secrets in Parameter Store
  • DNS provider account protected with 2FA
  • Weekly OS patching window, monthly budget alert
